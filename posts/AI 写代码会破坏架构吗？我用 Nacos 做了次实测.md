前段时间我连续写了两篇和 AI 生成代码质量有关的文章。第一篇[《不要 Review AI 写的代码》](/?post=不要review-ai写的代码)主要讨论，AI 生成代码越来越快以后，质量保障不能继续只靠人逐行看 Diff，应该把注意力移到验收标准和验证证据上。第二篇[《从代码验证到 Eval 体系：再谈 AI 生成代码的质量保障》](/?post=从代码验证到eval体系-再谈ai生成代码的质量保障)又往前走了一步，尝试把单次验证扩展成用例集、基线和持续回归。

文章发出去后，有读者在评论区提到：AI 写简单功能通常没什么压力，遇到复杂需求时，可能会选择直接、粗暴的实现方式。功能虽然完成了，原有的代码分层、模块职责和扩展边界也可能被破坏，后续维护成本会越来越高。

这个问题正好补上了前两篇文章没有展开的部分。验收标准和功能测试可以证明代码“做到了什么”，却很难单独回答另一个问题：**Claude Code、Codex 这类 Coding Agent 把功能做出来以后，项目原有架构变成了什么样？** 这里说的架构，主要指单个中大型应用内部的应用级架构，包括模块边界、数据归属、依赖方向、公共接口兼容、扩展机制和后台任务职责。微服务拆分、中间件选型和跨系统调用关系属于更高一层的系统架构，后面会说明本次实验为什么没有覆盖这个范围。

只围绕观点和假设讨论，得不出可靠结论。所以这次我找了一个知名的中大型开源项目，从它的 GitHub 仓库中挑选两个真实 Issue，让 Codex 按几种不同的使用方式各实现一次，再用提前确定的功能验收标准和架构评分规则检查结果。本次实验使用 Codex 作为 Coding Agent，底层模型为 gpt-5.6-sol，推理强度设置为 medium。每个任务、每种工作流只运行一次，这个规模可以用来分析案例中的失败原因，不能推导模型或 Coding Agent 的普遍成功率。

## 本次实验选择了什么项目和需求

[Nacos](https://github.com/alibaba/nacos) 是阿里开源的一个服务发现、配置管理和服务管理平台。它既包含面向用户的 Console 和公共 API，也包含配置持久化、数据库适配、插件扩展、集群一致性和后台任务等模块。一个局部需求经常会穿过多个层次：页面怎么传数据，公共模型把字段放在哪里，服务层如何处理，数据最终怎么保存，旧版本能否继续读取。这类项目可以观察 AI 完成功能时，能否沿用原有的分层和扩展方式。

为了让测试接近真实开发，我没有自己编造需求，直接从 Nacos 项目的真实 Issue 中选择了两个。

1. [Nacos Issue #13455](https://github.com/alibaba/nacos/issues/13455)：为 MCP Server 增加安全方案。用户导入 OpenAPI 或编辑 MCP 工具时，需要保存 HTTP、API Key、OAuth2、OIDC 等认证方式。这个需求会经过 Console、公共 API 模型、服务端持久化和再次编辑，可以观察数据应该归谁管理，以及跨层传递时会不会丢失。

2. [Nacos Issue #13453](https://github.com/alibaba/nacos/issues/13453)：为配置历史增加自动清理。Nacos 会保存配置变更历史，生产环境里的历史表可能增长到百万甚至千万行。新功能需要支持清理开关、保留天数和每天执行时间，同时处理分批删除、数据库差异、多节点部署时由哪一台 Nacos 服务器运行清理任务、任务出错后能否继续调度，以及 Nacos 停止运行时能否取消清理任务。

两个任务分别考验数据模型与职责归属，以及多节点下如何避免重复运行清理任务、数据库兼容、任务出错后能否继续调度和 Nacos 停止时能否取消任务。每一组实验都从同一个固定基线创建独立仓库，Agent 看不到其他组的代码。第一个任务已经存在社区合并方案，我在三组 AI 结果评分确定后才查看社区代码，避免它提前变成实现提示。

## 实验如何对比三种 Coding Agent 工作流

我把日常使用 Coding Agent 的方式分成 A、B、C 三组。三组使用相同的代码基线、Codex 版本、gpt-5.6-sol 模型和推理强度，差异来自输入信息和执行流程。

![直接实现、先做计划和架构保护闭环三种 Codex 工作流](/static/2026-07-19/codex-three-workflows.svg)

### A：拿到需求后直接实现

A 组模拟最常见的用法。Agent 只拿到脱敏后的原始需求，自行阅读代码、选择实现位置、修改文件并运行相关测试。我没有额外提供模块说明、架构约束和隐藏验收标准，任务结束后也没有增加独立 Review。这一组主要观察 Codex 在缺少额外工程约束时，会不会主动识别项目里的既有模式。

### B：先分析项目，再按自己的计划实现

B 组看到的需求和 A 组相同。第一阶段只能读代码，不能修改。Agent 需要先整理现有调用链、受影响文件、复用方式、兼容风险和测试计划。计划完成后恢复同一个会话，直接按照自己的判断实施，人不提供设计反馈。这一组主要观察“先读项目、先做计划”能带来多少改善，也能验证计划的局限：如果最初识别出的领域边界有问题，后续实现可能会把这条错误路线完成得更彻底。

### C：把架构约束放进完整闭环

C 组获得更完整的需求和验收条件，包括默认行为、旧数据兼容、非法输入、多节点部署时由哪一台服务器运行后台任务、批处理上限、任务出错后能否继续调度，以及 Nacos 停止时能否取消后台任务。Agent 在实现前必须输出七部分架构影响分析，明确现有调用链、模块边界、复用方式、兼容策略、风险、测试和预计修改范围。架构分析包含所有要求后才能开始改代码。初次实现结束后，我再启动一个全新上下文的 Codex，只读审查这次 Diff。审查问题必须包含具体文件、调用链和运行后果。原实现会话根据审查发现的问题修复一轮，然后重新运行统一验收。C 同时增加了需求信息、架构计划和独立审查，因此它代表一套完整使用方式，后面的结果无法单独归因于某一个步骤。

## 功能和架构分开评分

如果只看“测试有没有通过”，很容易把功能正确性和架构质量混在一起。我给每组保留两套结果。

第一套是功能验收标准，包含：

- 项目构建、格式和相关回归是否通过。
- 新需求的核心场景是否全部满足。
- 旧 JSON、旧配置和公共 API 是否兼容。
- 页面、数据库访问和跨模块调用是否真正生效。
- 隐藏场景是否暴露出公开测试没有覆盖的问题。

其中任何一项出现确定失败，这组实现就不能算完成功能。架构分仍然保留，用来解释它为什么失败。

第二套是 100 分架构评分表，把抽象的架构判断拆成六个可以逐项检查的维度：

| 评分维度 | 分值 | 主要检查内容 |
|---|---:|---|
| 模块边界与依赖方向 | 25 | 新概念放在哪一层，是否出现反向依赖和绕层访问 |
| 内聚性、耦合与职责归属 | 20 | 数据由谁负责，是否复制逻辑或建立平行实现 |
| 兼容性与可演化性 | 15 | 旧 API、旧 JSON、旧配置和扩展实现能否继续工作 |
| 可维护性与改动局部性 | 15 | 修改范围是否与需求匹配，是否扩散到无关模块 |
| 可靠性、集群行为与可运维性 | 15 | 异常、调度、多节点任务由哪台服务器运行、批处理、日志，以及任务如何启动和停止 |
| 测试设计与架构证据 | 10 | 是否覆盖功能要求、边界情况、异常和兼容场景 |

功能通过、没有严重边界问题、架构分达到 80，才判定为保持架构质量。“提升架构质量”的要求更高，需要在这次需求涉及的范围内减少重复实现、集中职责或补齐长期需要遵守的规则，同时控制改动范围。

最终结果如下：

| 任务 | A：直接实现 | B：先做计划 | C：架构保护闭环 |
|---|---:|---:|---:|
| MCP 安全方案 | 功能失败 / 61 分 | 功能失败 / 65 分 | 功能通过 / 91 分 |
| 配置历史自动清理 | 功能失败 / 70 分 | 功能通过 / 90 分 | 功能通过 / 91 分 |

两个任务中，A 组 0/2 通过，B 组 1/2 通过，C 组 2/2 通过。下面具体看它们分别发生了什么。

## 第一个 Issue 的实现评估：MCP 安全方案

第一个 Issue 要给 MCP 工具增加安全配置，例如 API Key、OAuth2 和 OIDC。这里可以把一个 MCP Server 简单理解为一组供 AI 调用的工具。Nacos 需要保存两类数据：一类是服务器的名称、地址和描述，另一类是工具的参数和认证方式。安全配置描述的是工具应该怎样被调用，所以应该跟着工具配置一起保存。

![A/B 与 C 对 MCP 安全方案数据归属的不同选择](/static/2026-07-19/mcp-security-ownership.svg)

A 和 B 都把安全配置放进了服务器资料。这样做以后，页面确实可以显示和编辑认证方式，但保存工具时走的是另一套数据。结果就是：用户第一次填写时页面正常，保存后再次打开，认证信息可能已经丢失。两组都没有通过“导入、保存、查询、编辑、再查询”的完整测试。

B 增加了表单、服务端校验和更多测试，架构分从 61 提升到 65，但数据仍然放错了位置。C 把安全配置放回工具配置，创建、导入、编辑和删除都使用同一条处理链路。C 的初版会丢掉部分 OAuth2、OIDC 和 OpenAPI 扩展信息，独立 Review 通过完整的数据往返发现了这个问题。修复以后，复杂安全配置可以原样保存和读取，C 通过全部功能验收，架构得分 91。

评分确定以后，我查看了已经合并的[社区 PR #13650](https://github.com/alibaba/nacos/pull/13650)。这个社区人工方案同样把安全配置放在工具配置中，说明 C 选择的数据位置符合项目原有设计。继续按照本次实验的完整测试检查，社区方案还有导入后丢字段、多个地方重复维护字段清单等问题。社区方案修改了 10 个文件，生产代码增加约 1091 行，测试只修改两行；C 的生产代码增加约 447 行，测试增加 224 行。

**按照本次实验提前确定的功能和架构标准，C 不逊于已经合并的社区人工方案，在数据完整性、改动规模和测试覆盖上表现更好。** 这个对比只针对当前 Issue 和本次验收范围，不代表 AI 实现普遍优于人工实现。它至少说明，只要上下文、架构约束和验证方法合适，AI 可以在中大型项目中完成质量较高的跨模块改动。

## 第二个 Issue 的实现评估：配置历史自动清理

第二个问题是：定时删除功能可以运行，到了生产环境却可能长时间占用线程、使用错误配置执行删除，或者在异常后停止调度。每天删除一次过期历史看起来只是一个定时任务，放到多节点、千万级数据量和多种数据库并存的 Nacos 中，还需要明确由哪一台 Nacos 服务器运行清理任务，避免多台服务器同时删除同一批数据；同时还要限制一次最多删除多少，处理配置错误、任务出错后的再次调度，以及 Nacos 停止运行时怎样取消定时任务并释放线程。

![配置历史自动清理的完整运行链路和三组实现差异](/static/2026-07-19/history-cleanup-flow.svg)

Nacos 已经有历史数据清理和多数据库适配能力，也有一套规则保证多台 Nacos 服务器中只有一台运行清理任务。三组都找到了这些现有机制，没有重新建立一套平行实现。差异主要出现在普通测试不容易覆盖的场景中：配置错误、每一批都达到删除上限、任务执行出错，以及 Nacos 停止时定时任务能否一起停止。

A 的 24 个相关 Maven 模块编译成功，Agent 自己选择的 85 个测试以及统一回归测试也全部通过。生产场景测试仍发现了四个问题：每一批都达到删除上限时，任务没有总批次或总耗时上限，可能长期占用执行后台任务的线程；保留天数或执行时间配置错误时，会换成默认值继续删除；旧版的保留天数配置升级后会失效；部分数据库实现每批删除前都要统计全部过期数据，面对大表成本较高，统计结果也不等于实际删除数量。因此 A 没有通过功能验收，架构得分 70。

B 在计划阶段识别了旧配置、只让一台服务器运行清理任务的规则和现有清理流程，最终把生产改动集中在负责配置管理的模块中。它为任务增加了异常处理和重新调度，功能通过，架构得分 90。它先统计过期数据量，再决定最多循环多少次；任务能够停止，但数据仍在变化或某一批少删时，统计结果可能与实际删除数量不一致，少量数据会留到第二天。

C 的首次实现同样先统计数据量。独立 Review 又发现两个问题：判断当前服务器是否负责清理时一旦出错，第二天的任务可能不会重新安排；旧接口还可能绕过新的删除限制。修复以后，C 限制了每批和每轮的删除量，让数据库返回每批实际删除的数量，并确保判断清理服务器或删除数据失败后仍会安排下一次任务。它最终通过功能验收，架构得分 91。

C 为获得准确删除数量，修改范围从 B 的一个生产模块、16 个文件扩大到三个生产模块、28 个文件。可靠性有所提高，跨模块改造也增加了维护成本，所以最终只比 B 高 1 分。这个结果说明架构检查既要发现运行风险，也要评估修复风险所需的改动范围。是否为了让删除数量完全准确而修改多个公共模块，需要根据以后能否复用这项能力来决定。

## 方法合适，AI 也能完成复杂架构改动

评论区担心 AI 遇到复杂功能后采用粗暴实现，这种情况在 A 组里发生了。两个直接实现样本都做出了大量看起来合理的代码，完整功能验收却是 0/2。C 组的两个需求都穿过多个模块，也都涉及兼容和运行时风险，最终功能验收 2/2 通过，架构得分都是 91。第一个任务还在实现这次需求时统一了原本分散的工具配置合并流程，测试密度和改动规模也优于社区参照。

**复杂需求交给 AI 不一定会破坏现有应用架构，结果取决于 Agent 获得的上下文、实施前需要回答的问题，以及完成以后面对什么外部反馈。** 从这六次实现里，我觉得有五个环节值得保留。

### 1. 先补充架构相关的验收条件

功能需求通常只写用户看得见的结果。Agent 还需要知道默认行为、非法输入、旧数据和旧配置、最大规模、多节点部署时由哪一台服务器运行后台任务、任务失败后怎样继续，以及 Nacos 停止时怎样取消任务。高风险需求里，这些内容应该在实现前明确。

### 2. 计划必须回答数据归属和调用链

“修改哪些文件、分几步完成”还不够。计划需要说明新数据应该由哪个模块负责、现有的主要处理路径、准备复用的抽象、公共兼容策略和预计修改模块。A/B 在 MCP 任务中的共同失败，根源就是数据归属判断错误。

### 3. 测试从开始到结束的完整流程

涉及数据字段的需求，可以准备“旧输入 → 新版本读取 → 编辑 → 再读取”的完整流程测试。后台任务需要覆盖每一批都达到删除上限、配置错误、当前这台服务器没有被选中运行任务、任务执行出错，以及 Nacos 停止运行时定时任务能否一起停止。如果项目支持多种数据库，至少要在两种数据库上分别验证，确保清理规则和结果一致。

### 4. 使用全新上下文做针对性 Review

Review 应该重点检查：数据在转换过程中会不会丢失，异常会不会导致任务停止调度，循环有没有上限，以及旧接口能不能绕过新规则。C 组两次独立 Review 发现的问题，普通功能测试都没有覆盖到。

### 5. 修复风险时同步控制改动范围

Reviewer 可以同时给出局部修复和基础设施演进两档方案。团队再决定接受一个范围小、有已知折中的实现，或为长期通用能力支付跨模块改造成本。这个决策仍然需要人负责。

低风险、局部 CRUD 没必要每次走完整闭环，B 组的计划流程已经足够轻量。公共模型、认证、持久化、集群、后台调度和数据迁移这些影响范围更大的需求，更适合增加完整验收条件和独立 Review。

## 成本、实验限制和架构范围

出于成本和效率考虑，这次采用了两个任务、三种工作流、每组运行一次的基础方案，并且只使用 Codex 和 gpt-5.6-sol。实验没有重复运行同一组，也没有更换 Agent 或模型对比；C 组同时增加了完整需求、架构计划和独立 Review，因此只能观察整套流程的结果，无法判断其中某一个环节单独贡献了多少。

完整闭环需要更多时间。第一个任务中，A 大约 15 分钟，B 约 20 分钟，C 约 30 分钟；第二个任务分别约为 18 分钟、30 分钟和 52 分钟。更多需求上下文、独立 Review 和修复会增加执行时间与 Token 消耗。这里选择这套方案，是为了用完整案例观察 Coding Agent 对架构的影响，没有把它设计成严格的模型能力测试。结论还需要在更多项目、Agent、模型和重复实验中验证。

本次测试主要覆盖应用级架构。在一个中大型代码库里，模块怎样分层、数据归谁管理、依赖朝哪个方向、公共接口如何兼容、后台任务应该由哪个模块或哪台服务器运行，都属于架构问题。大型分布式系统的系统级架构还包括服务拆分、系统职责与边界、跨系统调用关系、中间件选型、容量、容灾和部署拓扑。这些信息往往分散在多个仓库、运行平台和团队协作关系中，只提供一个代码仓库不足以评估 Agent 在这一层的架构能力。

在这两个 Nacos 案例中，直接实现留下了架构风险；加入完整验收条件、架构影响分析、跨层测试和独立 Review 后，Codex 完成了复杂改动，并保持了较高的应用级架构质量。前两篇文章把人的注意力从逐行阅读 AI 代码移到验收标准和验证证据，这次实验补充了架构层的验收内容：数据经过哪些边界，旧格式是否保持，后台任务由哪个模块或哪台服务器运行，失败后如何恢复，最大规模下何时停止。团队明确这些规则和改动范围，AI 也可以完成复杂功能，同时保持现有应用架构。
