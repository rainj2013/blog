目前基于 LLM 的工程化应用，很像互联网应用发展的早期阶段，底层能力快速变化，新的需求不断出现，大家一边做产品，一边发明框架、协议和开发范式。每隔一段时间，就有一套技术被当成未来；再过几年，其中一些成为基础设施，一些退回特定场景，还有一些逐渐退出主流。早期 Web 开发也经历过类似过程。后端从 CGI、JSP 这类动态页面方案走向成熟的 Web 框架，前端也从依赖 jQuery、Flash，发展到更多使用浏览器原生能力和组件化框架。一批技术因此逐渐退出主流，但它们当年都解决过真实问题。 **底层平台吸收了部分能力，新的抽象重新完成分工，原来显眼的技术才逐渐淡出。**

LLM 工程正在重演这个过程。前几年大家讨论 LangChain 和 RAG，后来是 Function Call、Agent 和 Workflow，再后来又出现 MCP、Context Engineering 和 Skill。最近 CLI、Harness Engineering 和 Loop Engineering 开始流行，仿佛大模型工程每隔几个月都要完成一次改朝换代。如果把这些词一个个拆开介绍，很容易写成一部概念词典。但我更关心的是另一件事，为什么它们会按照这个顺序出现？

回头看，有一个前提非常重要，**所有大模型工程化的工具、框架和范式，都是围绕当时主流模型的能力边界设计的。** 模型能否稳定遵循指令、输出结构化数据、选择工具、理解长上下文和完成多步任务，调用成本和响应速度能不能接受，都会直接决定应用层需要多少 Prompt、解析、编排和兜底。所以这几年发生的，是模型能力变化以后工程系统一次次重新分工。早期主要解决“怎么把一个只会生成文字、还不太稳定的模型接进应用”；后来解决“怎么让模型获取知识、调用工具并连续完成任务”；现在开始解决“怎么让一个能干活的 Agent 在真实环境里长期、稳定、可控地工作”。

## 第一阶段，让模型成为可用的软件组件

2022 到 2023 年的大模型应用开发，首先面对的是一个很基础的问题，模型很惊艳，但不像传统软件组件。调用数据库，开发者知道输入、输出和错误码；调用大模型，返回的却是一段概率生成的文本。同一个 Prompt 可能得到不同格式，要求输出 JSON 会多出解释，换一家模型又要改 API。对话历史怎么保存，文档怎么切分，向量库怎么接，结果怎么解析，当时都没有稳定答案。

LangChain 在这个阶段流行并不意外。它的 Python 包在 2022 年 10 月发布，当时整个生态都在快速变化。[LangChain 两周年回顾](https://blog.langchain.com/langchain-second-birthday)提到，它最早的目标就是把 LLM 连接到外部计算和数据源。Chain、Memory、Output Parser 和大量 Integration 先把不稳定的零件组织起来，让开发者能够快速做出应用。随着模型 SDK 和应用模式逐渐稳定，早期的厚封装开始显得多余，但 LangChain 当时承担的适配层和试验场作用仍然真实存在。后来简单封装被 SDK 吸收，复杂的状态管理则进入 LangGraph 这类运行时。

RAG 解决的是另一个硬约束，模型参数里没有企业内部知识，也不能及时知道新信息。2020 年的 [RAG 论文](https://arxiv.org/abs/2005.11401)讨论了参数化知识难以访问、更新和提供来源的问题，后来“向量库 + Top K”很快成为企业知识问答的标准配方。上线以后，文档是否过期、权限如何继承、多个来源冲突时相信谁，往往比向量数据库选型更难。长上下文减少了部分简单检索，外部知识需求仍然存在，RAG 也逐渐成为 Context Engineering 中按需提供事实的一种手段。

这一阶段还有一个很典型的变化。早期为了让模型调用工具，开发者会在 Prompt 里要求它输出 `Action`、工具名和参数，再用正则或 JSON Parser 拆出来。模型多说一句解释，整个链路就可能断掉。2023 年 OpenAI 发布 [Function Calling](https://openai.com/index/function-calling-and-other-api-updates/)，允许开发者用 JSON Schema 描述函数，由模型结构化地表达调用意图。后来 Structured Outputs 又进一步保证参数符合 Schema。原来由框架和 Prompt 勉强维持的输出格式，就这样被模型原生接口吸收了。这个例子很能说明大模型工程化的变化规律，**如果某一层主要是在补模型不会稳定做的事情，它很可能随着模型训练和 API 升级而变薄。**

## 第二阶段，让模型根据反馈连续行动

Function Call 让模型能够表达“下一步想调用什么”，但一次工具调用距离 Agent 还有一段距离。2022 年提出的 [ReAct](https://arxiv.org/abs/2210.03629)把推理、行动和观察放进连续循环，模型采取动作，读取环境反馈，再更新判断并决定继续或停止。模型拿到结果后重新判断状态，应用控制流才发生变化。

2023 年前后的 AutoGPT 把“自主 Agent”的预期推得很高。给模型一个目标，它自己规划、搜索、写文件、反思，理论上可以一直运行到任务完成。现实却经常是另外一种画面，Agent 在错误方向上反复尝试，工具结果越来越多，上下文越来越乱，Token 不断消耗，却没有可靠办法判断自己是否真的完成任务。Agent Loop 的方向本身没有错，当时的模型能力和外围系统却支撑不了那么高的自主性。模型规划和错误恢复不够稳定，工具接口不统一，状态只存在对话里，失败以后也缺少外部验证。把一个能走几步的模型放进 `while` 循环，不会自动得到一个能独立工作的 Agent。

后来 Workflow 重新受到重视，收回了一部分自由度。Anthropic 在 [《Building Effective Agents》](https://www.anthropic.com/engineering/building-effective-agents)里区分了两类系统，Workflow 由预先定义的代码路径组织模型和工具，Agent 则由模型动态决定过程。能提前确定的步骤，用 Workflow 更稳定；路径确实依赖中间结果时，再交给 Agent 判断。这轮调整是根据模型能力重新分配决策权。弱模型时期，分支、重试和路由更多写在代码里；模型变强以后，可以逐步把一些判断交还给模型。真实系统通常处在两者之间，外层有确定的权限、状态和检查点，检查点之间允许 Agent 自己探索。

MCP 也应该放在这个阶段理解。Function Call 解决模型如何表达调用意图，每个 AI 客户端仍然要分别接数据库、GitHub 和企业工具。Anthropic 在 2024 年开源 [Model Context Protocol](https://www.anthropic.com/news/model-context-protocol)，希望把这些连接标准化。从 Agent 的视角看，MCP、Function Call、Skill 和 CLI 都在解决“怎么把模型意图变成外部动作”，只是分别侧重结构化调用、跨客户端接入、SOP 与脚本、现有系统工具。一个 MCP Tool 会以类似 Function Call 的 Schema 暴露给模型，一份 Skill 也可能同时调用 MCP 和 CLI，这些方案存在明显重叠。

MCP 的适用范围会收缩。一条本地命令能完成的事，没有必要包装成 Server；跨客户端、跨组织、涉及认证和长期维护的连接仍然值得协议化。这个阶段重要的是控制流变化，以前代码调用模型，现在模型开始决定代码下一步调用什么，工程问题也随之转向“模型可以走多远，走错了怎么回来”。

## 第三阶段，构建 Agent 的运行与治理体系

最近一两年的模型已经能理解更复杂的指令，使用文件系统和 CLI，在多轮工具调用中保持目标，甚至连续工作数小时。模型变强以后，很多过去写在代码里的路由和步骤可以删掉，工程化却没有因此消失，反而开始向模型外部移动。Context Engineering 的流行很能说明这种变化。早期 Prompt Engineering 关注一句指令怎么写；Agent 每轮看到的内容却远不止 Prompt，还包括工具定义、历史消息、RAG 片段、Skill、文件、日志和刚刚产生的工具结果。Anthropic 在 [《Effective Context Engineering for AI Agents》](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)里把问题概括为从持续变化的信息中，选择当前应该进入有限上下文窗口的内容。

工程重点从编写完美的静态 Prompt 转向管理信息生命周期。项目规则可以稳定放在前面，当前任务状态需要随执行更新，长日志应该按需读取，旧历史可以压缩，失败证据必须保留，过时信息则要及时退出。之前我在[《纸上谈兵聊 Context Engineering》](/?post=纸上谈兵聊context-engineering)里讨论过这个问题，模型一次推理看到的上下文，就是应用为它临时构造的工作环境。长上下文会减少一些精细裁剪，但不会消除 Context Engineering。窗口装得下，不代表所有信息都值得放进去，更不代表模型能判断哪份文档是最新事实。上下文越长，工具执行产生的噪音越多，信息来源、权限和更新责任反而越重要。

Skill 和 CLI 代表了更轻的能力供给方式。模型可以读取 Skill 中的自然语言 SOP、参考资料和脚本，也能直接使用 Git、构建、测试等现有命令行工具。[Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)之所以可行，很大程度上得益于模型已经能把 Markdown 当作工作手册；值得固化的内容，是项目约束、组织流程、质量标准和可靠脚本。

更强的模型还可以现场创造工具。遇到项目特有的日志格式，它可以临时写脚本提取字段；需要批量修改配置时，可以生成转换程序，在样本上验证后执行，用完即弃。这会削弱预装大量专用 Tool 和 MCP Server 的必要性。未来 Agent 可能只需要文件读写、代码执行、网络和浏览器等通用原语，再按任务生成上层工具。边界同样明确，临时脚本无法凭空获得生产凭证和业务语义；涉及多人复用、敏感权限或不可逆副作用时，固定 Tool、MCP 契约和受控 Function Call 仍然更可靠。 **通用、稳定、高风险的能力由系统提供；低频、局部、可验证的能力由 Agent 临时生成。**

![Agent 使用系统提供的稳定能力与现场生成的一次性工具](/static/2026-07-05/agent-stable-and-disposable-tools.png)

当模型能够修改文件、运行命令和操作浏览器以后，Harness 开始成为更重要的概念。它让 Agent 看见代码、文档、界面、日志和指标，提供工具与隔离沙箱，管理上下文、权限、预算和状态，再用测试、Trace 和外部证据验证结果。OpenAI 的 [Harness Engineering 实践](https://openai.com/index/harness-engineering/)也把 UI、日志、指标和隔离 worktree 暴露给 Agent，让它能够直接观察和验证系统。 **模型越强，补模型智力的工程代码可能越少，管理真实副作用的工程系统反而越重要。** 一个能连续运行数小时、修改代码和访问业务系统的 Agent 出错，会留下真实影响，权限、隔离、审计、回滚和验证只会更加重要。

## Loop Engineering，自主执行继续向外扩了一层

最近又开始流行 Loop Engineering。按照目前 [Loop Engineering Guide](https://loopengineering.run/)的定义，系统会自行发现工作，把任务交给隔离环境中的 Agent，验证并保存结果，再通过定时器、Webhook 或队列触发下一轮。它比普通 Agent Loop 多关注一层，Agent Loop 处理任务内部的行动与反馈，Loop Engineering 处理任务之间的触发、持久状态和独立验证。

这套做法重新组合了 ReAct、Workflow、状态机、任务队列和 CI/CD 等已有机制。人的角色从每轮手动推动退到规则设计、异常处理和审批点。没有进度判断、退出条件和验证证据，Loop 只会自动重复失败；具备状态、预算、验证和人工门禁后，它就是正常的长期自动化系统。当前的使用场景和命名带来了新鲜感，循环、反馈和自动化本身早已有之。

## 会衰落的，通常是“替模型补智力”的那部分工程化

回头看这几年的变化，我觉得各种概念最后大致会走向三种结局。第一种是被模型或模型 API 吸收。早期为了得到 JSON 写的复杂 Prompt 和 Output Parser，后来被 Function Call 和 Structured Outputs 替代；一些手写路由、意图分类和任务拆分，也会随着模型判断能力增强而减少。现在模型还能根据任务临时写代码造 Tool，原来必须由开发者预先封装的一部分低频能力也会被进一步吸收。这类工程化主要在补模型能力，窗口期通常最短。

第二种是从热门概念沉入基础设施。外部事实不会自动进入模型，工具不会自动获得认证，跨系统连接也不会自动统一。RAG、MCP、状态存储和可观测性可能不再被当成产品卖点，却会像数据库连接池、消息队列和 API 网关一样，成为系统里普通但必要的部分。

第三种不但不会衰落，还会随着模型能力增强而加重。权限、隔离、事务、审计、回滚、验证和责任边界，都属于现实系统的控制问题。模型能做的事情越多，潜在副作用越大，这部分越需要工程约束。Harness、Eval 和治理体系主要落在这里。

![大模型工程化能力被模型吸收、沉入基础设施或持续增强的三种结局](/static/2026-07-05/llm-engineering-three-outcomes.png)

所以评价一个新概念，不能只看它最近火不火，也不能笼统地说它是模型能力不足时的脚手架。更有用的问题是下面这几个。

1. 它补的是模型不会做、模型不知道，还是系统不能让模型随便做？
2. 下一代模型变强以后，这个问题会消失，还是只会换一种实现？
3. 它是单个框架提供的便利封装，还是多个系统之间需要长期维护的契约？
4. 去掉它以后，复杂度真的消失了，还是被转移给应用代码、运维人员和最终用户？

如果主要在教模型理解和路由，它可能很快被模型吃掉；如果承担外部知识和系统连接，它会逐渐基础设施化；如果负责真实副作用和责任边界，它通常不会消失，只会换名字和实现。

## 接下来一段时间，工程重心可能继续往模型外部移动

基于当前已经出现的变化，我觉得接下来一段时间可能会看到三个方向。这里只是对短期趋势的外推，模型能力和产品形态一旦发生明显变化，判断也需要随之调整。

第一个方向是“少量通用原语 + 稳定系统接口 + 按需生成”。文件读写、代码执行、浏览器和网络访问会成为 Agent 的基础能力。低频、局部的工具由模型现场生成，用完即弃，因为生成一次性工具的成本已经很低；高频、跨团队和高风险能力继续通过固定 API、MCP 或其他受控协议提供。衡量工具能力的重点，也会从预装数量转向能否安全地发现、组合、生成和验证。

第二个方向是 Context Engineering 和 Harness 逐渐合并成 Agent 的运行平台。上下文管理会从摘要、压缩和检索走向状态治理，哪些信息是当前事实，谁负责更新，多个 Agent 如何共享，失败经验怎样进入下一轮。模型厂商和开源框架则会把工具调用、沙箱、状态保存、后台任务和 Trace 做成基础能力，应用团队重点定制权限、环境可见性、业务验证和失败恢复，未必还要从零实现 Agent Runtime。

第三个方向是产品交互从“人持续推动的逐轮对话”，走向“目标委托和结果验收”，Eval 也从离线测模型走向持续验证任务。Agent 产品需要任务队列、进度、证据和审批点，人负责定义目标与边界、处理异常并验收结果。测试、监控、Trace、线上 Bad Case 和业务结果会进入同一个反馈循环，模型输出只是中间产物，经过验证的任务结果才算交付。届时效率瓶颈可能转移到组织侧，能否提供清楚的目标、可访问的环境和机器可验证的完成标准。
