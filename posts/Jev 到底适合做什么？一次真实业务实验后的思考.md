相信很多人都听说了最近热门的 System One 模型 [Jev](https://docs.typesafe.ai/models) ，它不是一个常见的生成文本的模型，而是专注于类型化决策 + 概率的输出。Jev 只处理三种问题：Noul（是否）、Choice（选择）、Score（评分）。相比起大家熟悉的LLM，Jev 的输出延迟非常低，官方声称的延迟是 70–500 毫秒。基于它的这两个特征，Jev 在一些特定任务场景下很有想象空间。

我正好有一个真实的业务场景：面向用户的智能问答客服。用户的提问会被分成账号找回、充值到账、应用卡顿等十几个分类，一条提问可能包含多个意图。知识库大约有 200 多条，包含问题分类、问题描述和回复话术等信息，总长度两万多字。

我尝试在这个业务场景中引入了 Jev 模型，大幅降低了输入 token 消耗，但并没有降低整个链路的时延、费用，这个结果和我实验之前的预期差别比较大，也让我对 System One 这类模型适合放在什么位置，有了一些新的理解。

## 为什么想用 Jev

原来的流程比较简单：把系统提示词、整个知识库内容和玩家问题一起交给大模型，让它选择适用的知识，整理成客服回复。这个方案的问题很明显，每个用户输入都要携带两万多字的完整知识库，时延和 token 消耗量看起来有优化空间。

要减少输入，RAG 是一个很常见的选择：先从知识库里找到相关内容，再交给大模型回答。但仅靠语义相似度召回，还是会有一些错漏，特别是处理多意图问题的时候。如果引入前置意图识别、问题重写、混合检索再重排等等手段，对于这个小业务场景来说又未免过于复杂。所以之前的方案做了个取舍：既然整个知识库还能放进 context，那就全放进去，把“找知识”这件事交给大模型自己处理。

Jev 出现以后，我觉得这里似乎多了第三种选择。我们的知识库本身已经有现成的问题分类，如果它能比 RAG 更准确判断玩家的问题涉及哪些类别，再按类别取出知识注入到 prompt 中，避免每次都注入完整知识库，或许可以帮我节省很多输入 token。

## 实验设计与结果

为了做一个对照，我实现了三种方案：

- **全库注入**：也就是现有方案，每次提供全部知识，直接由 DeepSeek 生成回复。
- **Jev**：先判断问题涉及哪些知识分类，只注入这些分类下的知识。Jev 使用 Noul 模式，对 16 个已有类别分别做“是否需要”的判断，在一次 API 请求中提交。
- **RAG**：使用本地 embedding 模型为知识生成向量，以每个类别中相似度最高的知识作为这个类别的分数，最后选择排名前 3 的类别，把这些类别下的全部知识注入给 DeepSeek。

这里的 RAG 比较简单，本质上更接近一个基于 embedding 的 Knowledge Router，并不是一个完整的生产级 RAG 系统。它主要用来提供一个轻量的向量召回对照，不代表 Jev 和所有 RAG 方案的能力比较。

出于安全合规考虑，实验中使用的知识库和问答测试题不是真实生产数据，而是一套根据真实业务结构重新生成的数据。

知识库和测试用的问答对由 DeepSeek 生成，再经过 GPT-6 Sol 在独立上下文中进行评审。知识库规模与生产真实规模差不多：

```text
200 条知识
16 个知识分类
约 2.4 万字
```

用于测试的问答对一共 900 道，每一道都有对应的标准回复内容。


各组问题回答使用 DeepSeek 的 `deepseek-flash`。耗时从分类或检索开始，到完整回复结束；缓存命中率按输入 token 统计。

表表中的“合格回答”指 AI 盲评得到 PASS：所有用户诉求的要点都正确覆盖，没有编造知识库中不存在的内容，也没有随意向用户承诺处理结果。遗漏必要点记为部分合格，关键错误或主要诉求未处理记为不合格。

| 方案 | 完整回复平均耗时 | 合格回答 | 平均输入 token | 输入 token 缓存命中率 | 900 次推理费用 |
|---|---:|---:|---:|---:|---:|
| 全库注入 | 1.321 秒 | 882/900 | 18,683 | 98.76% | $0.1732 |
| Jev | 1.760 秒 | 782/900 | 2,803 | 87.02% | $0.3177 |
| RAG | 1.368 秒 | 775/900 | 4,412 | 93.50% | $0.1398 |

从输入长度看，Jev 的效果非常明显。平均输入从：```18683 token``` 下降到： ```2803 token ``` 减少约 85%。但完整回复平均耗时反而从： ```1.321 秒 ``` 增加到了： ```1.760 秒 ```，其中 Jev 单独调用平均耗时 0.347 秒，最终 LLM 平均耗时 1.412 秒。
**主要原因是Jev模型本身需要耗时，以及知识库动条目选择后导致的 prompt cache 命中率下降。**

![全库、Jev与固定 3 类 RAG 的完整回复耗时分解](/static/2026-09-27/jev-response-time.svg)

费用也出现了类似的情况，Jev 方案中的费用为 $0.3177，包含 **Jev 分类与 DeepSeek 生成两部分的合计**，900 次调用的已知费用估计拆开如下：

| 环节 | 费用 |
|---|---:|
| Jev：判断 16 个类别 | $0.1711 |
| DeepSeek：读取选中知识并生成回答 | $0.1466 |
| 合计 | $0.3177 |

相比全库注入的 $0.1732，DeepSeek 本身的生成费用确实下降了，大约下降 15.4%。但新增的 Jev 分类费用已经接近原来整条回答链路的费用，所以最终结果反而更贵。

## Token 少了 85%，为什么反而更慢、更贵？

全库注入虽然每次都有 18,683 个输入 token，但是它有一个很大的优势：**前面的内容几乎是不变的。** 每个请求基本都是：

```text
固定 System Prompt
+
固定完整知识库
+
变化的玩家问题
```

所以非常适合 prompt cache 前缀缓存，这次实验里，全库注入的缓存命中率达到了 98.76%。
而 Jev 方案每次都会根据问题选择不同类别，即使每个类别内部知识的内容和顺序完全固定，只要前面少了或者多了一个类别，后面的 Prompt 前缀就已经不同，所以 Jev 虽然把整个 Prompt 缩短了很多，但缓存命中率也从 98.76% 降到了 87.02%。

![稳定全库前缀与动态知识子集对缓存复用的影响示意](/static/2026-09-27/jev-prefix-cache.svg) 

另外，Router 本身也不是免费的，只有当后面的 DeepSeek 因为 Context 缩短，节省的时间和费用超过 Jev 模型分类花费的时间和费用，这个优化才有意义。

## 分类准确率不是这个任务真正的目标

“分类集合完全匹配”就是 AI 选出的类别和标准答案完全一样，不能多选，也不能漏选。例如正确类别是“账号找回、退款”，预测却多带了“游戏玩法”，分类集合就不完全正确；

Jev 不多不少完全准确选中分类的问题只有41%，大多数情况是多选了一些分类。但对于后面的客服大模型来说，这种错误其实没有那么严重。它只是多拿到了一部分无关知识，真正需要的知识仍然全部存在，大模型完全可能忽略多余的分类，最后给出正确答案。

在多意图问题上，Jev 比本实验中的 embedding 方案表现更好。按测试题应该包含的知识类别统计：

```text
Jev Recall    ≈ 83%
RAG Recall    ≈ 70%
```

315 道多意图题中：

```text
Jev 合格回答：228
RAG 合格回答：204
```

说明 Jev 虽然经常会多选类别，但在同时识别多个诉求这件事上，确实比这次简单的向量检索更加稳定。当然，这个结果只代表本文的实验条件。RAG 如果加入更好的 embedding、Query Rewrite、混合检索或者 Reranker，结果可能完全不同。
目前 Jev 官方也明确说明主要训练语言是英语，中文并不是它最擅长的语言。这很可能也是本次分类效果不够理想的原因之一。我还是比较期待以后出现更多中文能力更好的 System One 模型。

另外，我还试了一下支持多语言的本地 System One 模型 Laya。 小批量跑了 30 道题，其中只有 16 道最终回答合格，因此没有继续跑完整的 900 道测试。

## 重新理解 System One 模型的定位

做这个实验之前，我把 Jev 当成一个 **更快的 Knowledge Router**，做完以后，我现在觉得这可能不是 System One 最有价值的位置。因为这个架构本质上只是在原来昂贵的大模型调用之前，又增加了一次模型调用。它能不能产生价值，完全取决于后面究竟省掉了多少东西。无论 Jev 怎么判断，最后还是一定要调用 LLM，它做的事情只是让 LLM 少接收一些输入。这种优化我现在更愿意叫**Context Routing**，但 System One 可能更适合做另外一种事情：**Compute Routing**。例如：

![jev 路由示意](/static/2026-09-27/jev-compute-routing-diagram.png)


简单的问题：

```text
用户明确要求转人工
```

判断完成以后，直接进入转人工流程。

不需要再调用大模型。

又比如：

```text
是不是退款问题？
是不是账号安全问题？
是不是包含个人信息？
是不是需要人工审核？
```

这些判断结果本身就可以直接影响系统下一步，这时候一次很快的 Jev 调用，有机会真正替代：

```text
一次 LLM
一次 Agent
一次复杂 Workflow
```

而不只是把下一次调用的 Prompt 从 10,000 token 缩成 3,000 token。**它既保留传统分类器输出范围小、速度快的特点，又能像大模型一样能理解比较自由的自然语言条件，这可能才是 System One 真正值得探索的地方**。
