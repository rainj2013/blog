[上一次](/?post=vibe个工具系列02-coding-agent-终端工作台luna-mux)分享了 Coding Agent 终端工作台 [Luna mux](https://github.com/rainj2013/luna-mux)。我用了一段时间后，补上了一些觉得有必要的功能，也修复了一些使用中遇到的问题，现在已经更新到了 v0.5.0。这篇文章继续分享一下这些更新，也聊聊做这些功能时的一些设计想法。

## 数据库窗格

现在一个项目会话里，除了可以创建本地终端和 SSH 远程终端窗格，还可以新建数据库窗格。支持 SQLite、MySQL / MariaDB 和 PostgreSQL。

常用的数据库客户端功能基本都有，包括连接管理、查看表字段和索引等结构信息、执行 SQL、分页查询、SQL 补全和数据编辑，也支持 SQL 导入导出。还有专门为 Agent 操控设计的读写权限控制功能：可以设为只读，也可以对 DDL、DML 类型的写操作做单次允许/持续允许执行的细粒度权限控制。

和 Luna mux 的其他功能一样，数据库窗格也可以通过 Luna Mux MCP 交给 Agent 操作。Agent 可以自己创建数据库窗格，查看界面，把 SQL 填进编辑器，执行 SQL。用户能直接看到它写的 SQL 和查询结果，也可以随时自己修改、继续操作。

这样一个 Coding Agent、一个 SSH 终端、一个数据库、一个浏览器，就可以一起工作了。Agent 可以在授权范围内自主操作所有工具，人类随时可观察、介入。

## 增强 Agent 的终端操作

原来不同窗格之间的通信，只是简单支持读取另一个窗格的内容，以及向里面写入文字。Agent 可以看看输出、输入一些命令，但要连续操作交互式程序，还需要花不少精力从输出中判断当前状态，操作也容易出错。

这次设计了一套终端交互协议，除了内容读写，还支持发送按键事件、读取屏幕和光标位置等信息。同时优化了等待、超时重试和输入协调机制，减少重复输入和多个 Agent 操作时的干扰，让终端交互更加安全可控，用户也可以随时接管。

## 浏览器控制和 WebMCP

浏览器控制在第一个版本就已经有了，这次主要改善了启动等待和预热重试，减少 Chrome 还没准备好时出现的偶发失败。

内置的 agent-browser 做了升级，并增加了 [WebMCP](https://developer.chrome.com/docs/ai/webmcp) 支持：网页可以像mcp协议一样注册工具，Agent 通过 agent-browser 发现后就可以调用，减少解析 DOM 和逐个操作控件的步骤。

浏览器仍然以独立的 Chrome 窗口运行，用户可以直接查看页面，遇到登录验证或者需要手工调整时，可以随时接手。

## 会话、窗格和其他改进

会话和窗格增加了拖拽排序，窗格还支持最小化，布局调整也更方便了。另外修复了一些终端输入、Agent 状态通知和跨平台兼容问题，补上了软件检查更新等小功能。

## 下载地址

Luna mux 的源码和安装包都在 [GitHub](https://github.com/rainj2013/luna-mux)，最新版本是 [v0.5.0](https://github.com/rainj2013/luna-mux/releases/tag/v0.5.0)。支持 macOS 的 Intel 和 Apple Silicon，以及 Windows。已经安装的用户也可以从应用的“关于”页面检查更新，打开对应的 Release 下载。

## 碎碎念

上一篇文章结尾说过，AI 原生时代的软件，当用户觉得一个功能应该可以交给 Agent 时，它就应该提供相应的操作接口。Luna Mux这次新加的功能也是面向人类和 AI 分别设计友好交互体验的。

其实终端控制、Web 访问、数据库读写等操作，Agent 完全可以在后台默默完成。但在当前的 AI 发展进度下，我依旧希望在一个可观测的 UI 界面上看到 AI 的操作步骤和进度，必要时接手控制，控制权的交接要足够丝滑，就像汽车辅助驾驶那样。

Agent 的通用 Computer Use 能力可以让 Agent 像人一样通过屏幕和输入设备操作各种软件，我很期待这个方向。但现在它的成本和性能还不够友好。对于终端、数据库、浏览器这些常用工具，我更愿意先做一些定制，让软件主动告诉 Agent 有哪些对象、可以执行什么操作，同时把过程和结果展示在人的 UI 里。

Luna mux 的所有功能都是在这两个理念指导下设计的，既为人设计，也为 Agent 设计。
