相信很多人都听说了最近热门的 System One 模型 [Jev](https://docs.typesafe.ai/models) ，它不是一个常见的生成文本的模型，而是专注于类型化决策 + 概率的输出。Jev 只处理三种问题：Noul（是否）、Choice（选择）、Score（评分）。相比起大家熟悉的LLM，Jev 的输出延迟非常低，官方声称的延迟是 70–500 毫秒。基于它的这两个特征，Jev 在一些特定任务场景下很有想象空间，本文将介绍我在一个真实业务场景中，引入 Jev 实测的效果和一些总结。

## 为什么没有用 RAG

我准备了一个真实的业务场景：面向用户的智能问答客服。用户的提问可能涉及账号找回、充值到账、道具消耗、游戏玩法、应用卡顿等分类，可能包含多个意图。我们的知识库大约有 200 多条，包含问题分类、问题描述和回复话术等信息，总长度两万多字。

原来的处理方式比较直接：把系统提示词、整个知识库内容和玩家问题一起交给大模型，让它选择适用的知识，整理成客服回复。这样做实现简单，但每个问题都带上两万多字的完整知识库，时延和 token 消耗量都比较高。

要减少输入，RAG 是一个很常见的选择：先从知识库里找到相关内容，再交给大模型回答。但仅靠语义相似度召回，还是会有一些错漏，特别是处理多意图问题的时候。如果引入前置意图识别、混合检索再重排等等手段，对于这个小业务场景来说又未免过于复杂。对于这种小型的知识库，完整注入到 prompt 算是准确性与工程成本的取舍。后面的实验也用一个本地 embedding 模型和内存向量矩阵，做了最简单的检索对照。

## Jev 实验准备
Jev 吸引我的地方，是它专门做判断和分类，而我们的知识库已经有现成的问题分类。如果它能比 RAG 更准确判断玩家的问题涉及哪些类别，再按类别取出知识注入到 prompt 中，避免每次都注入完整知识库，或许可以帮助我优化这个业务场景的 token 消耗量与耗时。

**从目的上看，这里用 Jev 做的事，与 RAG 中的知识召回很相似：都是先挑出可能需要的知识，再交给文本生成模型。** 我设计了一个对比实验，比较全库回答、Jev 分类和 RAG 检索：

- **全库注入**：即现有全量注入知识库的模式，每次提供全部知识，直接由 DeepSeek 生成回复。
- **Jev**：先分类，只注入选中类别的知识；固定阈值 0.5，最多保留 3 类。
- **RAG，固定取 3 类**：用本地 embedding 模型做向量检索，以类别内条目的最高相似度作为类别分数，取排名前 3 类，注入这些类别的全部知识，再由 DeepSeek 回复。

其中 Jev 使用 Noul 模式对 16 个类别分别做是否判断，在一次 API 请求中提交，再以固定 0.5 阈值保留最多 3 类，以支持多意图，不强制选满。

出于安全合规的考虑，实验用的知识库和问答测试题非真实生产数据，而是一套由 deepseek 生成，经过 gpt-6-sol 独立上下文评审的数据。知识库规模仍然是 200 条知识、16 个类别，知识内容约 2.4 万字。用于测试的问答对包含 900 道测试题和标准回复内容。

## 实验结果分析

各组最终生成统一使用 DeepSeek 的 `deepseek-flash`。耗时从分类或检索开始，到完整回复结束；缓存命中率按输入 token 统计。

表表中的“合格回答”指 AI 盲评得到 PASS：所有用户诉求的要点都正确覆盖，没有编造知识库中不存在的内容，也没有随意向用户承诺处理结果。遗漏必要点记为部分合格，关键错误或主要诉求未处理记为不合格。

| 方案 | 完整回复平均耗时 | 合格回答 | 平均输入 token | 输入 token 缓存命中率 | 900 次推理费用 |
|---|---:|---:|---:|---:|---:|
| 全库注入 | 1.321 秒 | 882/900 | 18,683 | 98.76% | $0.1732 |
| Jev | 1.760 秒 | 782/900 | 2,803 | 87.02% | $0.3177 |
| RAG | 1.368 秒 | 775/900 | 4,412 | 93.50% | $0.1398 |

Jev 将平均输入降到 2,803 token，比整个知识库注入少约 85.00%。JEV 单独调用平均 0.347 秒，完整回复平均 1.760 秒，其中最终 LLM 平均 1.412 秒。输入明显缩小了，但由于本轮总耗时仍高于全库的 1.321 秒；**主要原因是Jev模型本身需要耗时，以及知识库动条目选择后导致的 prompt cache 命中率下降。**

![全库、Jev与固定 3 类 RAG 的完整回复耗时分解](/static/2026-09-27/jev-response-time.svg)

Jev 方案中的费用为 $0.3177，包含 **Jev 分类与 DeepSeek 生成两部分的合计**，900 次调用的已知费用估计拆开如下：

| 环节 | 费用 |
|---|---:|
| Jev：判断 16 个类别 | $0.1711 |
| DeepSeek：读取选中知识并生成回答 | $0.1466 |
| 合计 | $0.3177 |

与全库回答的 $0.1732 相比，DeepSeek 生成费用下降了约 15.4%，但新增的 Jev 分类费几乎等于原来整条回答链路的费用，所以合计仍更贵。

## 动态注入的知识库降低了prompt cache 命中率

prompt cache 依赖前缀匹配，整个知识库注入的方案每次都带着相同的系统提示词和知识库内容，只在后面换玩家问题，更容易命中缓存。而Jev 方案每次挑出的类别可能不同，知识条目的组合也会变。即使条目文字完全没改、排序也固定，前面少了一条知识，后面的输入前缀就已经不同了，从而降低了缓存命中率。

## 分类准确率分析

“分类集合完全匹配”就是 AI 选出的类别和标准答案完全一样，不能多选，也不能漏选。例如正确类别是“账号找回、退款”，预测却多带了“游戏玩法”，分类集合就不完全正确；但所需知识条目仍在，回答模型可能忽略多余的知识条目，最终得到合格的答案。

Jev 不多不少完全准确选中分类的问题只有41%，大多数情况是多选了一些分类。原因有两个：
1. 我为了平衡最终回答的准确性，选择了比较低的 Noul 模式选择的阈值，这导致分类被选中的概率比较大。
2. 中文支持不足可能是原因之一，Jev 官方明确说明英语为主要训练语言，中文场景下的准确度可能会下降。

不过，在多意图问题上，Jev 的分类表现比本实验的 RAG 更好：按这些题目应该选中的类别统计，Jev 找到了约 83%，RAG 约 70%。最终 315 道多意图题中，Jev 有 228 道回答合格，RAG 为 204 道。这说明它虽然在总费用和耗时上不占优，但在识别多个诉求上仍有一定价值。当然，这个结果只代表本次对照，不能推广到所有 RAG 方案。

我还选择了支持多语言的本地部署 Laya 模型进行了尝试，但小批量跑了 30 道题，回答准确率只有16/30，因此没有进一步全量跑测试。希望开源社区还有更多优秀的、支持中文的 System one 模型涌现。

## Jev 更适合什么样的任务？

我现在更倾向于把 Jev 用在这样的地方：读一段内容，做几个明确的判断，程序拿到结果就能决定下一步。这也接近官方介绍的用法：把较大的任务拆成具体判断，再由代码组合处理结果。

例如，把工单交给哪个团队，用户有没有要求转人工，一段内容是否包含个人信息，或者候选材料是否符合某个筛选条件。这些任务的输出范围比较明确，不一定需要模型写一段解释。Choice 可以选择一个处理流程，Noul 可以分别检查多个条件，Score 则适合按事先定义的标准评分。

值得关注的是判断之后能省掉什么工作。把工单直接送到合适的处理流程，或者让条件明确的问题直接返回已有话术，才有机会省掉后续调用。如果只是先做一次判断，然后仍然调用同一个大模型完成原来的工作，就像这次实验一样，额外的判断可能反而增加等待和费用。

## 最后的结论

在本次中文客服问答场景中，引入 Jev 对问题预分类，没有带来整体上的优势。输入虽然减少了，多意图识别也比本次 RAG 对照更好，但完整回复更慢、总费用更高，回答合格率也低于全库注入。对于这套规模不大的知识库，我暂时没有看到引入它的必要。

当前版本的 Jev 主要以英语训练，中文支持还有提升空间。不过，这次实验的结果并不代表 System One 这类专门做判断的模型没有价值。工单分流、条件检查等任务，判断结果能直接决定下一步，可能更适合它们。我仍然期待未来出现更多这类模型，尤其是中文支持更好的版本，再看看它们在具体业务里能带来什么收益。
